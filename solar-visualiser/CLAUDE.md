# Solar 3D Visualiser

Static site, no build step. Open `index.html` directly (`file://` works) or serve with any static server. Classic `<script>` tags only — no ES modules, no bundler.

## Module pattern

Every JS file (except `vendor/` and `data/`) attaches to a shared global namespace:

```js
window.SolarViz = window.SolarViz || {};
window.SolarViz.xyz = ...
```

Load order is dependency order — see `<script>` tags in `index.html`. Don't reorder without checking what each module reads off `window.SolarViz`.

## Property loading

`js/properties.js` registers properties, reads `?property=original|3broomroad`,
loads only that property's classic scripts in order, and exposes
`SolarViz.propertyReady`. `main.js` awaits it before reading any data. The
selector reloads the page on address changes; building storage keeps its
existing address-specific key. Header and summary values come from SITE_DATA.
DSM metadata is supplied per property as `__DSM_META__`; it is no longer fixed
inside coordinates.js. Camera and lighting use the property's ground altitude.

`3broomroad-data/property-bundle.js` is generated by
`scripts/prepare-property.py` from raw solar/OS JSON, cached DSM/aerial files,
image-manifest.json and photos/floorplan. See that folder's README for the
height-estimation method and coverage limits. Do not edit generated bundles.
The gallery now includes the floorplan reference. An empty floorplan `floors`
array means there is no generic manifest import. A property-specific reviewed
adapter may supply automatic room mapping; never borrow another property's annotations. New model exports carry `propertyKey`; imports reject a mismatch,
and legacy exports without that field remain supported.

`node tests/properties.test.js` checks both properties' offline assets, DSM
metadata, coordinate frames, watertight geometry, boundary-edge coverage and
floor slices. Run it after changing loading, preparation or shared geometry.
Point-touching roof components get separate vertices for separate closed shells;
collinear wall runs stop at the loop seam before the last/first merge.

## Files

- `vendor/three.min.js`, `vendor/OrbitControls.js` — three.js r160 (UMD/global build) + OrbitControls.
- `data/site-data.js` — `window.SITE_DATA` (property/roof/panel data), `window.__DSM_B64__` (base64 heightmap), `window.__AERIAL_DATAURL__` (aerial photo). **This is the future API swap point** — currently hardcoded, will eventually be fetched from a backend instead.
- `data/image-data.js` — `window.IMAGE_DATA`: manifest over `data/images/` (listing photos + floorplan), produced by an offline AI ingest pass (currently hand-authored by Claude reading the images; same backend swap point as site-data). Photo entries carry kind/room guesses and feature bboxes; the floorplan entry carries per-floor room rectangles, labels and printed dimensions in image px. **Immutable source suggestions** — the app never writes back. Reviewed room adapters may now seed remote hypotheses automatically under the user-authorised workflow; other suggestions retain explicit adoption.
- `data/image-blobs.js` — `window.__IMAGE_DATAURLS__`: every file in `data/images/` embedded as a data URL, keyed by image id. **Generated — regenerate from `data/images/`, never edit.** Exists because of the file:// contract (see Gotchas): plain file paths can't feed WebGL textures or be pixel-read from a canvas. All image consumers resolve through `window.SolarViz.imageUrl(im)` (defined in `gallery.js`: prefers the embedded data URL, falls back to the file path) — new code must too.
- `data/images/` — the raw listing images (webp) + `floorplan.webp`.
- `data/rebuild-solid.json` — export of the regularised solid's wall panels (ids, plan segments, top profiles, eave/ridge heights) consumed by the Blender/IFC scripts at the repo root; not read by the web app.
- `js/geometry-utils.js` — shape/plane-fitting helpers.
- `js/coordinates.js` — DSM decoding + lon/lat ↔ scene-coordinate conversion.
- `js/scene-setup.js` — scene/camera/renderer/controls/lights.
- `js/terrain.js` — terrain mesh + aerial texture.
- `js/panels.js` — solar panel meshes.
- `js/roof-faces.js` — roof face meshes + array list sidebar.
- `js/obstructions.js` — obstruction meshes.
- `js/plan-draw.js` — shared top-down drawing engine (ortho plan camera, click-to-place vertices, banner, Enter/Esc/Backspace keys). One session at a time; used by scaffolding and the building-model wall drawing.
- `js/scaffolding.js` — scaffold designer: draw vertices on the ground (top-down), auto-generates tube/board scaffold to the eaves, costs it at length × billed height (whole 2m lifts) × £/m² rate.
- `js/building/` — building model derived from the roof faces:
  - `geometry.js` — pure geometry helpers (plane fits/intersections, polygon ops, ear clipping, mesh slicing, polygon splitting, watertight check). **No THREE/DOM** — also loaded by the node tests via `module.exports`.
  - `solid.js` — regularisation pipeline: cluster roof vertices, snap them to plane intersections, level eaves, chain + square-up the footprint, extrude walls to ground → watertight indexed mesh. Compute half is pure; mesh builders need THREE. Consecutive boundary edges that are collinear in plan (gable ends: eave corner → apex → step → eave corner) are snapped exactly onto their chord and merged into ONE wall panel with a stepped `topProfile` — so a gable is a single plane a window can sit anywhere on; the triangle soup still uses the per-edge vertices, so watertightness is untouched. User footprint edits are parametric inputs: `footprintOffsets` (per-vertex drags) and `footprintDeleted` (corner removals, taken out of the loop AND the roof face rings so the mesh stays closed), both keyed to pre-edit loop indices via `footprintOrigIdx`.
  - `floors.js` — slices the solid into storeys (slab outlines from horizontal mesh cross-sections) + slab meshes.
  - `rooms.js` — room partitioning: floors start as one room, each drawn divider wall splits one room in two (rooms re-derived from the divider list, so undo = pop + replay). Wall-draw mode stays active after each split (Esc or the button exits) and pops a room-type prompt for the newly carved room. Also room types (kitchen/living/bedroom/bathroom/hallway/storage → tint + label) and the thick exterior-wall band shown while a floor is being edited (selecting a floor isolates it: shell + other floors hidden, openings filtered to that floor). Gotcha: transforms that place things on walls must be proper rotations — a makeBasis(dir, up, normal) basis is left-handed (a reflection) on half the walls; use `setFromUnitVectors(+Z, normal)` or an explicit right-handed z = x×y.
  - `floorplan.js` — floorplan import (pure, node-testable): fits a similarity transform from plan-pixel space onto a floor outline (scale from the plan's printed room dimensions, orientation searched over 4 rotations × mirror, translation minimising deviation from the expected roof-overhang rim), converts the plan's rooms into one carve polyline per room (manifest order — T-junction walls land on walls carved earlier), and replays them through `deriveRooms` — so imported rooms are ordinary dividers: editable, persisted and undoable like hand-drawn ones. Walls stay exactly on the building axes; where the roof outline and the plan disagree at a corner, only a short hinged tail bends to close the room (beyond ~1.2 m sideways the wall fails loudly instead). `refitDividers` re-snaps stored walls after the outline changes (footprint edits, storey changes) or a wall is moved. Note the floor outline is the **roof** footprint (~0.4 m proud of the plan's walls all round); the fit expects that rim.
  - `openings.js` — windows (real holes in wall panels + glass + frame) and radiators, in wall-local (u, v) coords. `clampWindow` is profile-aware via `panelTopMin`: on a merged gable panel the height limit is the top profile over the window's own u-span, so a window mid-gable can rise toward the apex. Doors are windows with `kind: 'door'` (sill clamps to 0, rendered from the floor).
  - `gallery.js` — property-photo gallery (thumbnail grid + lightbox) for the ASHP sidebar; reads IMAGE_DATA only.
  - `photomatch.js` — camera-pose recovery for exterior photos (pure, node-testable): named landmarks derived from the solid (eave/ground corners keyed on cluster ids, gable apexes, ridge ends), a pinhole solver (Levenberg–Marquardt over position/rotation/focal from multiple seeds) and wireframe projection. Deadband priors (level camera, person/pole height, normal-to-wide lens) keep sparse near-coplanar point sets out of the telephoto-vs-wide PnP ambiguity without biasing well-constrained solves. Matches are stored as landmark ids + normalised pixels — frame-independent, so the same data solves in node tests (property-centred frame) and the app (DSM-centred frame).
  - `photomatch-ui.js` — the human half: per-photo match panel with AI-suggested draggable dots, the model wireframe re-projected live over the photo (trust = the wireframe visibly locking on), per-dot error colours, add/remove landmarks. When suggestions are bad, "Align view" overlays the photo on the 3D view so the user orbits until the model lines up — that camera becomes the pose (no auto-refine on confirm: the dots may be the wrong part, and the wireframe from the aligned pose shows where they should go; dot releases warm-refine rather than reseed so the established pose family sticks). Accepted matches persist in buildingState, render as camera frustums with photo thumbnails, and "Stand here" flies to the photographer's position and cross-fades the photo at the solved focal length (frustums hide while standing in one — the thumbnail sprite otherwise fills the lens). Re-solves automatically when the solid rebuilds.
  - `facade.js` — facade projection + opening editor: bakes accepted photo poses onto the wall panels (per-texel back-projection through each pose with a ray-cast against the solid's own triangles, so near walls don't paint far ones; best-rmse photo wins per texel) into CanvasTextures that drape onto the existing wall geometry — ShapeGeometry uvs are wall metres, mapped with texture repeat/offset, so punched window holes keep the texture. The wall editor shows the baked facade flat with a metre grid: a dragged rectangle IS the opening in wall coordinates — a floating Window/Door chooser appears beside the rectangle (min drag 25 cm, metric not screen px), sky above a gable's top profile is masked out, and existing openings are drawn back in. Per-wall photo ▲/▼ buttons nudge the projection's vertical sampling ±5 cm (persisted as `state.facadeAdjust[wallId]`) to push roof bleed back above the eave; the wall's photo loads lazily and re-bakes on arrival.
  - `building-ui.js` — sidebar section, edit modes, localStorage persistence + JSON export/import. All 3D state is derived; only settings + edits persist. Editing: click a divider wall to select it (drag sideways to move — attached walls re-snap; delete via the button; room names/types survive id churn via centroid remapping in `remapRoomMeta`). "Edit footprint" shows draggable handles on the main loop's vertices; committed drags persist as `state.footprintOffsets` (per-vertex [dx, dz], invalidated if the regularised vertex count changes) and rebuild the whole chain — solid → floors → rooms (refit) → openings (rebind). Neighbour edges axis-snap during the drag so the footprint stays square. A plain click (< 3 cm of movement) selects a handle instead, revealing "Delete corner" — deletions persist as `state.footprintDeleted` (pre-edit loop indices, matching `solid.footprintOrigIdx`); "Reset footprint edits" clears both edit kinds.
- `js/interactions.js` — hover tooltips + camera fly-to animation.
- `js/ui-controls.js` — sidebar toggle/slider bindings.
- `js/mode-switcher.js` — top mode toggle (Solar / ASHP / EVC): swaps sidebar panels (`#panel-solar` / `#panel-ashp` / `#panel-evc`) and 3D layers. Solar layers are hidden in ASHP mode and re-applied from the View Layers checkboxes on return; ASHP gates the building model via `building.setActive()`. Last mode persists in localStorage (`viz-mode`).
- `js/main.js` — entry point, wires everything together, render loop.

## Manual roof editing

**ASHP → Roof Geometry → Edit roof geometry** opens the aerial-plan editor.
`js/building/roof-edit.js` is pure UMD geometry/state code; `roof-edit-ui.js`
is the SVG editor and disposable three.js preview. The canonical starting
faces are derived once from the source survey with the default solid settings.
Corrections are sparse replacements/deletions against those stable source face
IDs plus explicitly added faces, stored in `buildingState.roofEdits` and exported
with the rest of the model. All corner coordinates are metres from the property
reference point (X east, Z south, Y above ground), independent of the DSM origin.
Existing footprint corrections are folded into the draft when present.

Drafts support corner dragging, numeric position/height edits, shared-corner
moves, edge insertion, corner deletion, face drawing/redrawing/deletion,
corner-to-corner splits, triangulation, pitch/facing controls anchored to a
selected corner, undo/redo, reset and cancel. Photos and the floorplan resolve
through `SolarViz.imageUrl`; click a reference to enlarge it within the editor.
The one-metre grid, pan/zoom and orbitable 3D preview support visual checks.

**Refit selected to DSM / Refit all to DSM** fit heights and pitches in the draft
without moving plan corners. `js/building/roof-dsm.js` is pure UMD and samples
the original decoded DSM (never the flattened/capped display terrain), at pixel
centres in the property frame. It trims 0.3 m at edges, rejects nodata/outliers
with deterministic RANSAC, then jointly fits connected planar faces with exact
shared-corner constraints and robust least squares. Selected includes the whole
connected roof group; lower disconnected roofs fit independently. Faces without
reliable samples use their previous plane slopes as soft shape priors (no
invented DSM observations or absolute height anchors). Supported neighbours
anchor their heights; exact shared-edge constraints can alter the old slopes.
These inferred faces appear purple and are reported as "Guided shape", with
pitch/height changes and no claimed DSM residual. Undo/redo retain these labels.
A group with no reliable face remains unchanged with one group-level message;
incompatible ridge positions or residuals above 0.35 m also leave it unchanged. Reports show retained samples and before/after residuals;
these measure DSM agreement, not survey accuracy. Cyan original DSM points can
be overlaid in the translucent preview. Refit is undoable and only Apply saves.
Trace one polygon per planar slope before refitting; small dormers may require
measured heights where the DSM lacks sufficient interior samples.

`node tests/roof-dsm.test.js` checks plane recovery, noisy/nodata samples, pixel
centres and crop origins, joined ridges, independent lower extensions, refused
fits, mixed observed/sparse connected faces, groups with no DSM evidence,
input immutability, saved replay and both real property datasets.

Apply validates finite heights, polygon area/crossings, overlaps above 0.05 m²,
watertightness and consistent orientation. Non-planarity above 4 cm is reported
for review; the exact vertex surface is retained rather than silently fitted.
Shared edges are split at exact T-junctions. `preserveVertices` in `solid.js`
skips plane-intersection snapping, eave levelling, footprint squaring and wall
run projection for corrected geometry. Automatic settings and the separate
footprint editor are disabled while manual roofs are active. Solar mode keeps
the source survey. All corrected roof loops participate in terrain flattening.

Applying roof corrections increments `roofRevision`, marks accepted photo
matches `roofNeedsReview`, archives their old clicks and clears live poses and
landmark indices. Match suggestions from the original topology are suppressed;
new matches are explicitly accepted against the rebuilt landmarks. Facade
projection excludes stale matches. Resetting to detections also requires review.
This avoids reusing a cluster index that now identifies a different corner.

`node tests/roof-edit.test.js` checks replay/reset, both real datasets, exact
coordinates in different frames, lower extensions, T-junctions, splitting,
shared corners, invalid polygons/overlaps and stale-match invalidation.

## Broom Road reconstruction experiment

`reconstruction.html` is an isolated candidate-review workbench, linked from the
Broom Road ASHP sidebar. `reconstruction/model.py` defines a semantic building
hypothesis; `reconstruction/fit.py` fits bounded parameters and camera poses to
assistant-annotated front photos, printed plan dimensions and the original DSM.
The runner generates `3broomroad-data/reconstruction/{run.json,bundle.js,candidate.json}`.
The viewer consumes the classic-script bundle and embedded imagery, so HTTP and
file:// both work. It does not write building localStorage or apply candidates.
Candidate exports have their own schema and are not building-state imports.

`js/building/reconstruction.js` is pure UMD projection/frame math, also checked
against the Python output. `reconstruction-ui.js` displays stage comparisons,
photo observations, check-image residuals, inferred openings, a 3D preview and
aerial/plan references. Named semantic landmarks survive parameter fitting.
Window check positions do not enter geometry fitting; their camera uses roof,
door and separate vertical-edge directions. Camera vertical image shift handles
cropped/perspective-corrected listing images. Check views were inspected during
development, so they are diagnostic, not an untouched benchmark.

Marigold V2 was investigated but not run (documented Linux/CUDA requirements;
this host is macOS ARM). No monocular-depth values influence the result. Externally generated raw normals now enter the lower rear extension refinement as weak constraints. The
optional `reconstruction/prepare_depth_job.py` packages input photos and GPU job
instructions. `reconstruction/revise_rear.py` replays the user-confirmed pair of
mono-pitch rear roofs from `front-fit-baseline.json`, holding the front fit and
cameras fixed. `run.py` then adds rear camera checks and an evidence/survey bundle.
`align_rear.py` excludes the lower roof checks from pose fitting; both current
rear fits hit camera bounds and fail validation. Rear pitches and dimensions, basement depth and secondary openings
remain explicitly uncertain. See `reconstruction/README.md`.

Run `node tests/reconstruction.test.js` after changing the experiment: it checks
all candidate shells, planar faces, stable landmarks, projection parity, source
hashes, evidence separation, offline bundle parity and regression on real photos.

## Tests

`node tests/building-geometry.test.js` — checks the solid is watertight on the real site data, slices are closed loops, polygon splitting conserves area; also the merged walls (a gable is one panel with a multi-point top profile, interior vertices sit exactly on the chord, every boundary edge is covered by exactly one panel) and that footprint offsets/corner deletion keep the solid watertight. Run after touching anything in `js/building/geometry.js`, `solid.js` or `floors.js`.

`node tests/building-floorplan.test.js` — fits the bundled floorplan onto the derived floors and checks the imported rooms (scale, fit score, divider replay, labels/types). Run after touching `js/building/floorplan.js` or the floorplan section of `data/image-data.js`.

`node tests/building-photomatch.test.js` — synthetic pose round-trips plus the manifest's real photo correspondences (rmse, camera position sanity; `needsReview` matches only have to solve). Run after touching `js/building/photomatch.js` or the match blocks in `data/image-data.js`.

## Gotchas

- `vendor/three.min.js` must define global `window.THREE` (UMD build, r160). If `THREE` is undefined at startup, the page shows "THREE.js failed to load." — check this file wasn't swapped for an ES-module build.
- **The file:// contract.** The page must keep working when opened directly from disk. Under `file://`, Chrome's tainted-canvas rules block both WebGL texture uploads of plain file images and canvas `getImageData` on them — symptoms are silent (white sprites, a bare "Script error" with no stack). So every image the app projects, textures or pixel-reads is embedded as a data URL (`data/image-blobs.js`, `__AERIAL_DATAURL__` in site-data) and resolved via `window.SolarViz.imageUrl(im)`. Never point a `TextureLoader`, `Image`+canvas read, or sprite at a raw `data/images/...` path.
- Headless verification of file:// pages (CDP/puppeteer-style) additionally needs Chrome launched with `--allow-file-access-from-files`.

## Geometry preparation replaces the calculation UI

The user's scope is room/envelope geometry, remote hypotheses and targeted site
refinement. `geometry-prep.js` (pure UMD) and `geometry-prep-ui.js` replace the
former heat-loss UI. The page calls only `heatLoss.derive` for quantity geometry;
its earlier arithmetic remains unused. Do not reintroduce thermal input requirements.

`state.geometryPrep` stores remote room/surface edits, immutable input checkpoints,
append-only observations and acceptance/rejection decisions. `geometryPrep.review`
produces remote/current comparisons. Only accepted fields on a matching geometry
and remote-input revision apply. Surface classifications include party/external,
unheated/ground and unknown; internal adjacency derives from the room layout.
`preserveHistory` protects survey records during model restoration and JSON import.

`Listing-plan estimates` offers a provisional twelve-room Broom schedule using
traced polygons, level-specific plan scale and explicitly assumed clear height.
It does not automatically generate a metric 3D interior or declare basement coverage.
`Priority site checks` ranks coverage/boundary ambiguity first, then dimension
uncertainty and large openings; collinear segments become one wall-run check.
No global "surveyed" flag: accepted measurements yield a partly site-refined schedule.
See `reconstruction/ASHP-WORKBENCH.md`; run `tests/geometry-prep.test.js` and the
HTTP/file:// `tests/browser-ashp-workflow.cjs` via `tests/browser-review.cjs`.

## Plan intake and lower-ground context

`plan-intake.js` is a pure, property-gated Broom Road floorplan adapter, loaded
following `floorplan.js` and before `building-ui.js`. It supplies explicit ordered
wall paths and stable source-room label points. Preview is overhead; source imagery
uses the existing data-URL underlay. Strict imports require every wall and label to
resolve before Apply. Settings store dividers, source room links and the transform.
The legacy manifest importer is unchanged for the original property.

`buildingProject.lowerGround` derives a separate closed lower-ground volume from
explicitly selected main/bay roof faces and an assumed depth. It contributes wall
panels/openings and an appended level without renumbering ground/first. Quantities
use physical floor adjacency. Count/attic edits are disabled while it exists.
`terrain-cutout.js` clips the display at exact polygons and preserves outside
heights/UVs/normals; it never edits the raw DSM. ASHP uses uncapped DSM context,
while solar mode retains its roof-cap display. The optional basement frontage
section is labelled a display cutaway. Mesh and sampling coordinates use raster
cell centres consistently.

Tests: `plan-intake.test.js`, `terrain-cutout.test.js`, existing geometry/quantity
suites and the HTTP/file:// `browser-review.cjs` workflow. See WORKFLOW.md for
plan provenance, limitations, and the degenerate-triangle clipping regression.

## Automatic room hypotheses and workspace navigation

The user authorised automatic room mapping (superseding the per-floor confirmation
step above for reviewed adapters). `automatic-rooms.js` is pure UMD: it prepares
missing Broom Road layouts and provisional lower ground, validates labels/coverage,
preserves existing edits and persists a mapping report/version. `project-ui.js`
runs it on existing reconstructed model load and on adoption. A fresh build requires
no room-import dialogue; deliberately replacing an edited model retains a preview.
It never auto-accepts survey evidence. Source/geometry changes retain old mappings
and their diagnostics rather than silently overwriting room work.

`workspace-ui.js` controls the House/Rooms/Survey panels, including direct survey
navigation and revealing relevant editors after scene interaction. All original
control IDs stay unique and mounted; specialist editors are in native details.
`building-ui.js` exposes layout notifications for accurate room-count summaries.
Run `automatic-rooms.test.js` and `browser-review.cjs` for these flows.

DSM facade fringe: `terrainCutout.cut` also accepts `{poly, aboveY}` masks. They
subtract only the portion above the datum inside the plan polygon and interpolate
all attributes at intersections. The Broom Road default replacement includes a
frontage-only mask generated by `terrainCutout.frontage`; it preserves DSM
samples below the display cutoff (the ground-floor datum, lowered to clear any
modelled basement opening). The separate basement cutaway removes the same section at all heights.
Never reintroduce a uniform neighbour buffer or validate only the cutaway view.
